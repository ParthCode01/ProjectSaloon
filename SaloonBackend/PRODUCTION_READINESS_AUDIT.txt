1. ARCHITECTURE SUMMARY
--------------------------------------------------------------------------------
Layered monolith, single shared MySQL database with row-level multi-tenancy.

     Controller -> Service -> Repository (Spring Data JPA) -> MySQL
                     ^
              SecurityContext (JWT via stateless filter chain)

Tenant isolation = service-layer pattern, NOT filters/interceptors/schemas.

- Packages : config, controller, dto, entity, exception, repository,
             security, service
- Roles    : ROLE_OWNER, ROLE_CUSTOMER, ROLE_STYLIST
- Entities :
    User -> Tenant (M:1)
    Stylist -> Tenant (M:1), -> User (1:1), <-> Booking (1:N)
    Treatment -> Tenant (M:1)
    Booking -> User / Treatment / Stylist / Tenant (all M:1)
- Auth flow: email/password -> BCrypt verify -> JWT (HS256, 24h, subject=email,
  NO tenant/role claims) -> JwtAuthenticationFilter loads User from DB per request
- Multi-tenancy: every repository query takes Tenant (or User) as scoping arg;
  user resolved from SecurityContext each request
- External deps: MySQL, Redis (declared but UNUSED — @EnableCaching, no @Cacheable)
- Config: application.properties (env placeholders for DB creds + JWT secret = GOOD),
  .env untracked = GOOD, ddl-auto=update
- Deployment: nothing Docker-related exists; no profiles; no actuator; no logging

Request flow example (booking):
  POST /api/bookings -> BookingController -> BookingService.createBooking
  -> resolve user from SecurityContext -> tenant-scoped findByIdAndTenant for
     treatment + stylist -> conflict queries -> save -> BookingResponse.

3. SECURITY AUDIT
--------------------------------------------------------------------------------

3a. AUTHENTICATION
  Registration        : Works. Owner signup creates Tenant+Owner; dup email -> 409. Customer signup public + tenantId OK.
  Password hashing    : BCrypt, encoder bean correct.
  JWT generation      : subject + iat + exp, HS256, 24h. No role/tenant claims -> DB hit per request (acceptable for MVP).
  Invalid/expired JWT : 500, not 401. extractUsername() throws ExpiredJwtException / MalformedJwtException /
                        SignatureException uncaught inside the filter. Expired/malformed tokens must produce 401.
  Deleted user w/ valid token : UserDetailService.loadUserByUsername throws raw RuntimeException -> 500.
  Stateless           : CSRF off, no sessions — appropriate for JWT.

3b. AUTHORIZATION (two big problems)
  1) SecurityConfig has NO @EnableMethodSecurity. Every @PreAuthorize in
     BookingController is SILENTLY IGNORED. Effect once ambiguous mapping is fixed:
       - PATCH /api/bookings/{id}/confirm      -> any CUSTOMER of tenant can confirm any pending booking
                                                (confirmBooking has no service-level role check)
       - PATCH /api/bookings/{id}/completed    -> any role can call (status stays for non-owners, but 200 no-op)
       - PATCH /api/bookings/{id}/cancel       -> redundant with PUT status
       - GET /api/bookings (owner tenant view) -> redundant method anyway (section 2)
  2) Role authorization for Treatments missing entirely. SecurityConfig rules:
       /api/bookings/**   OWNER|CUSTOMER
       /api/stylists/**   OWNER
       everything else    authenticated()
     => POST/DELETE/PUT /api/treatments/** reachable by CUSTOMERs — they can
        create/delete/update the salon treatment catalog.

  Endpoint role audit:
    POST /api/stylists        intended OWNER, actual OWNER (URL rule) .................. OK
    GET  /api/stylists        intended OWNER(?), actual OWNER only — customers can't browse stylists
    ALL  /api/treatments/**   intended OWNER mutations, actual any authenticated ........ BROKEN
    PATCH confirm/completed   intended OWNER, actual any authenticated ................. BROKEN (once mapped)
    PATCH cancel              intended OWNER/CUSTOMER, actual any authenticated ....... BROKEN (has service ownership check)
    GET  /api/tenants         intended public (onboarding), actual any authenticated .. design decision
    GET  /api/stylists/me/bookings   STYLIST — listed before /api/stylists/** so OK .... OK

3c. MULTI-TENANCY / IDOR REVIEW
  Strong / tenant-safe (verified query by query):
    - createBooking: treatment + stylist fetched via findByIdAndTenant(user's tenant)
        -> cannot book another tenant's resources; user/stylist same tenant by construction
    - getBookingById, deleteBooking, updateBookingStatus:
        OWNER -> findByIdAndTenant, CUSTOMER -> findByIdAndUser
    - getAllBookings, getMyTenantBookings, getMyUserBookings: scoped by tenant/user
    - StylistService / TreatmentService all use findByIdAndTenant / findByTenant
    - Conflict queries use the (already tenant-scoped) stylist object -> no cross-tenant leakage
    - cancelBooking: tenant-scoped fetch + explicit ownership check
        -> same-tenant cross-customer cancel -> AccessDeniedException

  Weak / at risk (NOT cross-tenant, but privilege escalation within a tenant):
    - confirmBooking, completeBooking, getMyTenantBookings rely 100% on dead @PreAuthorize
        -> once app runs, any customer in the tenant can confirm bookings.
        Fix: add @EnableMethodSecurity (or method-level role checks).
    - GET /api/tenants exposes every tenant id/name/address to any authenticated user
        -> fine for public directory, but know that's what you're shipping.

  VERDICT: TRUE cross-tenant IDOR (Tenant A reads/modifies Tenant B data) is NOT
  present. Vulnerabilities are horizontal (within-tenant role escalation), all
  tracing back to method security being off.

9. CONCURRENCY / RACE-CONDITION REVIEW
--------------------------------------------------------------------------------
YES, the double-booking race exists.

    Request A: SELECT conflicts -> none
    Request B: SELECT conflicts -> none
    Request A: INSERT
    Request B: INSERT   <- both succeed, same stylist + time

Nothing serializes check-then-insert: no @Transactional (each query is its own
transaction, so the window is wide), no pessimistic lock, no unique constraint.

Real production concern? For an MVP single-instance deployment the probability is
low but non-zero (two POS clicks / two customers same hot slot). It is a
CORRECTNESS bug, not availability: worst case = overbooked stylist.

Simplest appropriate fix:
  - @Transactional on createBooking
  - pessimistic lock on the stylist row inside:
        SELECT ... FROM stylist WHERE id=? AND tenant_id=? FOR UPDATE
    (add @Lock(LockModeType.PESSIMISTIC_WRITE) to a repo method)
  Then run conflict checks + insert in that transaction. Serializes bookings per
  stylist -> second request's conflict check sees first request's insert.
  - Optional second-line guard: unique index on (stylist_id, start_time, status).

Must fix before MVP? DEFERRABLE but cheap -> I'd fix it (10 lines) since conflict
logic is otherwise the strongest part of the app.
